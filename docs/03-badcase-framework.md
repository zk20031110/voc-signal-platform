# Badcase 归因框架

> 归因是 AI PM 最核心的日常工作之一。改 Prompt 之前先归因，是这个岗位和「会调 API 的人」的分界线。

## 一、五类归因

| 归因类别 | 判定特征 | 典型修法 | 修复成本 |
| --- | --- | --- | --- |
| 检索问题 | 单条都判对了，就是串不成信号；知识库没命中；跨渠道没关联上 | 换检索策略、补知识库、修正关联键 | 中 |
| 模型问题 | 语义理解本身出错；输出结构损坏（漏卡、字段缺失、JSON 不合法） | 换模型、加输出校验、加 schema 约束 | 低到中 |
| Prompt 问题 | 指令边界没写清，模型在两个可接受答案之间选了另一头 | 补枚举定义、加正反例、收紧约束 | 低 |
| 数据问题 | 语料本身残缺或歧义：没有用户标识、文本过短、渠道字段缺失 | 补元数据、加数据质量校验、丢弃无效样本 | 高 |
| 产品设计问题 | 期望值本身站不住，或指标定义与业务目标错位 | 改标注口径、改指标定义、重新拆需求 | 最高 |

排序逻辑是：越靠上的越容易在系统内部解决，越靠下的越需要回到需求本身。

## 二、为什么这个顺序不能反

一个真实例子。

现象：跨渠道矛盾的 5 条用例，只通过 2 条。

错误做法：直接改 Prompt，加一句「请注意同一用户的不同渠道反馈」。改完再跑，通过 3 条，然后卡住——因为剩下 2 条的问题根本不在 Prompt。

正确做法是按顺序排查：

1. 先看检索：同一用户的记录有没有被关联起来？如果 Agent1 输出的 `customer_ref` 是 null，或者上游根本没把多渠道数据放在同一批次里，改一百遍 Prompt 都没用。
2. 再看模型：关联上的那几条，模型有没有理解「不喜欢」和「用两天就坏」的矛盾？如果理解了但没输出，是结构问题。
3. 再看 Prompt：矛盾还原的字段定义是不是不够明确？`conflict_detail` 该写什么、写到什么粒度，有没有说清。
4. 再看数据：退款原因字段是不是被平台截断了？用户标识是不是脱敏后不可用了？
5. 最后才问：这个期望值对吗？「穿透退款理由」这个要求是不是本身超出了合理范围？

这个顺序的价值在于：它强迫你先排除「系统能力问题」，再怀疑「需求定义问题」，避免把系统缺陷误判成需求变更。

## 三、归因记录表

每条 Badcase 建议记录以下字段，便于后续统计分析：

| 字段 | 说明 |
| --- | --- |
| case_id | 关联评测集编号 |
| 现象 | 期望值 vs 实际输出 |
| 归因类别 | 五类之一 |
| 归因依据 | 为什么这么判，要有可复现的证据 |
| 是否复现 | 重跑是否稳定复现，偶发失败通常是模型随机性 |
| 修法 | 具体动作，不能写「优化一下」 |
| 回归结果 | 修复后全量 30 条的变化 |

## 四、原型里的实现

评测看板对失败用例自动给出**系统建议归因**，规则如下：

1. Agent1 或 Agent2 没有返回结果 → 模型问题
2. 该用例带 `debatable` 标记 → 产品设计问题
3. 期望高风险且属于跨渠道用例 → 检索问题（跨渠道记录注入链路嫌疑最大）
4. 标签、情感、新信号全对，只错在风险等级 → Prompt 问题（判定边界的松紧问题）
5. 属于歧义或对抗场景 → 数据问题
6. 标签判对但情感判错 → Prompt 问题
7. 其余 → 模型问题

界面上每个失败用例都可以手动改判。自动建议只是省一步操作，**归因本身是判断，不是计算**，最终要由人落定。

## 五、一个反直觉的提醒

不是所有 Badcase 都要修。

如果一条用例的失败率在多次重跑中都不稳定，说明它是模型随机性，不是系统性缺陷。这类用例应该标记为「观察」，而不是花力气优化——优化的收益会被随机性吃掉，还可能因为过拟合这条样本而损害其他用例。

真正值得投入的，是**稳定复现、且对应真实业务损失**的那一类。
