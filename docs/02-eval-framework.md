# 评测体系设计

> 指标口径与计算方式见 `eval/metrics.md`，本文件讲的是**为什么这样设计评测集**。

## 一、评测集要覆盖的五类场景

一个只包含正常差评的评测集，测不出任何有价值的东西。真正能暴露问题的，是边界。

| 场景 | 为什么必须放进来 | 典型样本 |
| --- | --- | --- |
| 高频正常反馈 | 这是基本盘。模型不应为了显得能干而过度解读平常的一句话 | 「快递第三天就到了，包装完好」 |
| 语义相同但表述不同 | 暴露「关键词匹配式实现」。同一个故障有十种说法 | 充电口松 / 接口接触不良 / 要按住才有反应 |
| 跨渠道矛盾 | 单渠道建模的根本盲区，也是本项目的核心差异点 | 退款写「不喜欢」，客服记录写「用两天就坏了」 |
| 知识缺失场景 | 预设标签体系覆盖不了的新信号，检验标签体系能否自我发现盲区 | 「炸壶」「爆盖」这类现象黑话 |
| 歧义反馈 | 反讽、信息不足、褒贬混合，检验是否硬猜 | 「呵呵，真棒，用一次就再也不想买了」 |

另外补一组对抗与边界样本：广告导流、无意义字符、假设性咨询（「如果过敏能退吗」）、多问题混合。这些是企业真实数据里必有的脏数据。

## 二、为什么要专门设计「跨渠道矛盾」

这是整个评测集里我最看重的一类，原因有三层：

**第一层，它验证的是归因而不是分类。** 单看退款记录「不喜欢」，判成「其他」是正确答案。只有把同一用户的多渠道记录关联起来，才可能得出「涂层脱落」这个真实问题。这考验的不是模型的语言能力，而是流水线的关联设计。

**第二层，它对应真实的业务损失。** 商家按退款理由做归因，会得出「用户偏好问题」的结论，然后继续发货。而真实原因如果是工艺缺陷，每一件发出的货都在制造新的差评。

**第三层，它天然区分了「接了大模型」和「做了产品」。** 一个直接调 API 的 Demo 拿到「不喜欢」只会照着字面回答。能穿透它的系统，必须有跨渠道关联、有知识库比对、有归因框架。

## 三、标注口径要先定，再评

评测集的期望值由谁定、按什么口径定，比样本数量更重要。

本项目的三条标注原则：

1. **以可复现的产品或流程缺陷为准。** 主观偏好、预期不符、使用不当，都不算「质量」问题。
2. **允许存在多个可接受答案。** 例如「客服帮我解决了充电口松动的问题」既可能是服务问题也可能是质量线索，两边的标注都接受。强行二选一只会制造假精度。
3. **承认标注本身有争议。** 标 `debatable` 的用例，失败时优先归因为产品设计问题，而不是模型能力问题。

第 3 条是 AI PM 的日常：很多 Badcase 不是模型错了，是需求没定清楚。

## 四、评测不是一次性的

评测集本身会过期。某个场景连续多轮全通过，说明它已经失去区分度，应该补更难的样本。

本项目的迭代节奏：

1. 改动任一 Agent 的 Prompt 或切换模型，重跑全量 30 条
2. 新增 Badcase，先归因，再改 Prompt
3. 回归全量，确认没有把别的用例改坏
4. 定期检查哪些场景已经全通过，补充更难的样本

## 五、业务层指标怎么才算真

模型层指标（标签命中率、F1）可以离线算。但「商家处理效率提升」「差评响应时间缩短」这类业务指标，离线算不出来。

本作品集的处理方式是：**只定义口径，不编造数字**。

| 业务指标 | 口径定义 | 需要什么才能验证 |
| --- | --- | --- |
| 商家处理效率提升 | 从收到反馈到做出处置决策的中位耗时变化 | 线上 A/B，对照组用原有流程 |
| 差评响应时间 | 从差评产生到商家首次动作的时间间隔 | 接入平台评价接口 |
| 风险信号采纳率 | 人工复核后判定为「确实需要处理」的信号占比 | 人工复核记录回流 |
| 信号提前量 | 风险信号触发时间 早于 差评率异常上升的时间 | 需要至少一个完整销售周期 |

面试里主动说清「这几个指标我现在验证不了，因为缺少线上对照组」，比给一个好看但站不住的数字更可信。
