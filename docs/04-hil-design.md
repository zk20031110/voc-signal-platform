# Human-in-the-loop 设计

> 不同 Agent 的自主权限不同。权限分级不是技术选择，是风险选择。

## 一、权限矩阵

| 环节 | 自主级别 | 触发人工的条件 | 判定理由 |
| --- | --- | --- | --- |
| Agent1 采集标注 | 全自动 | 置信度低于阈值时进入抽检队列 | 标错一条反馈的代价是可控的，且会被下游和人工复查 |
| Agent2 风险识别与归因 | 条件自动 | 安全类、品牌声誉类、监管风险类，强制转人工 | 漏掉一个安全信号的代价不可逆 |
| Agent3 行动建议 | 只生成建议 | 不执行任何写操作，采纳权完全归商家 | 建议错了商家会自己判断；系统自动执行错了无法挽回 |

一句话概括：**风险越高，自主级别越低。**

## 二、为什么不让模型自动执行

一个很自然的想法是：既然已经识别出问题了，为什么不让系统自动联系供应商、自动下架、自动给用户发补偿？

三条理由：

1. **责任无法归属。** 自动下架造成的销售损失，责任在谁？模型不能承担责任，最终还是要人来背，那就应该由人来决定。
2. **上下文不完整。** 模型看到的是语料，看不到库存、账期、供应商关系、平台规则。缺了这些，动作可能是错的。
3. **一旦自动化，人就不看了。** 这是最危险的一条。自动化会消解人的注意力，等到系统出错时，已经没有人有能力接住。

所以 Agent3 的 Prompt 里写死了：只输出建议，不做任何自动执行动作。

## 三、强制人工复核的触发条件

以下情况无条件进入人工复核队列，不依赖模型判断：

- 人身安全：起火、漏电、烫伤、过敏、儿童误食
- 食品安全：变质、异味、异物
- 品牌与合规：平台投诉、监管举报、媒体曝光迹象
- 模型自述低置信度：`need_human_review` 为 true

前三条是业务红线，与模型能力无关。即使模型判错了风险等级，只要语料里出现了这些关键词，就应该被拦下来。

## 四、人工复核要看得见什么

复核不是让审核员重新读一遍模型输出。界面必须提供：

- **原始语料。** 每一条证据都能点回到用户的原话，不需要切换系统
- **归因依据。** 模型为什么这么判，推理过程可被质疑
- **渠道分布。** 信号来自几个渠道、几条证据，避免被单条极端样本带偏
- **知识库命中。** 是否匹配到历史案例，匹配到哪一条
- **模型置信度。** 让审核员知道哪部分需要重点看

这五样东西合起来，才构成一次真正的复核。少了任何一项，复核都会退化成盲目点「同意」。

## 五、复核结果要回流

复核不是终点，而是训练数据的来源。

| 复核结论 | 回流去向 |
| --- | --- |
| 确认是风险 | 进入知识库，作为后续同类信号的匹配依据 |
| 判定为误报 | 进入 Prompt 的负例，用于收紧同类信号的判定 |
| 判定为漏报（人工发现的） | 补充进评测集，并归因到检索或 Prompt 环节 |
| 归因有争议 | 标注为 `debatable`，触发标注口径的复核 |

没有回流，人工复核就只是一次性的成本支出，不会让系统变好。

## 六、本原型的实现程度

原型不包含真实的人工复核工作台，但在界面上完整呈现了 HIL 的触发链路：

- Agent2 输出 `need_human_review`，涉及安全 / 健康 / 品牌声誉的信号必须置为 true
- 结论区对标记过的信号显示「强制人工复核」标签
- Agent3 输出 `human_review_note`，说明本条是否需要人工确认后再推送
- 预警推送在界面上只做展示，不执行真实推送

这是刻意的取舍：**先说清权限边界，再做界面**。反过来做，权限就会变成事后补丁。
