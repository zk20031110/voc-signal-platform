# 三 Agent 协作架构

## 一、链路总览

```
反馈批次（含 customer_ref 与渠道）
      |
      v
[ Agent1 信号采集与标注 ]        逐条调用 · 全自动
      8 类预设标签多选 + 情感 + 实体抽取 + 新信号标记
      out: 标注 JSON（外层挂 feedback_id / customer_ref）
      |
      v
[ Agent2 风险识别与归因 ]        逐条调用 · 高风险转人工
      输入 = 反馈卡 + 7 天历史信号库 + 同一用户在其他渠道的记录
      out: risk_level / risk_reason / attribution / need_human_review
      |
      v
[ 聚合层 ]                       纯规则 · 无模型调用
      按「风险等级 + 主标签」归组，合并证据与归因
      |
      v
[ Agent3 洞察生成与行动建议 ]     逐组调用 · 只建议不执行
      out: Markdown 洞察报告（证据链含语料编号，可下钻）
      |
      v
结构化报告 + 可追溯证据链
```

完整字段定义见 `prompts/00-shared-schema.md`。

## 二、相对原始 Prompt 的三处增补

三个 Agent 的 Prompt 以原始版本为基线，只在原文上做加法：

| 编号 | 位置 | 增补内容 | 解决什么问题 |
| --- | --- | --- | --- |
| 1 | Agent2 · 输入 | 注入该用户在其他渠道的历史反馈，并提示交叉验证说法是否一致 | 原始 Prompt 一次只接收一张卡，跨渠道矛盾在架构上不可能被发现 |
| 2 | Agent1 · 输出外层 | 挂载 `feedback_id` 与 `customer_ref` | 卡片需要可追溯；跨渠道关联需要用户标识 |
| 3 | Agent3 · 证据链 | 增加一行「语料编号：F001, F002」 | 让洞察可以下钻回原始语料 |

除上述三处，其余内容未做任何改动。

## 三、为什么需要聚合层

Agent2 逐条输出风险判断，Agent3 接收的是「一个」风险识别结果。如果直接对每条反馈调用一次 Agent3，同一批次会产生多份高度重复的报告。

聚合层是一个纯规则组件：

1. 按「风险等级 + 主标签」把风险结果分组
2. 组内取最严重的风险等级
3. 合并组内所有 `feedback_id`、渠道与原始文本，形成证据链
4. 高风险组内只要有一条 `need_human_review` 为 true，该组即为 true
5. 只为「高」与「观察」两组调用 Agent3；常规不生成报告

这是刻意的设计取舍：**模型负责判断，规则负责归并。** 把归并交给模型只会增加成本和不确定性。

## 四、跨渠道矛盾：本项目的核心场景

同一个用户名下，退款渠道写「不喜欢」，客服渠道说的是「用了两天就坏了」。单渠道看，前者是噪声；关联之后，它是被掩盖的质量缺陷。

这条链路依赖三个环节同时成立：

1. Agent1 的输出外层带上 `customer_ref`（增补 2）
2. 聚合前的注入逻辑能找回同一用户的其他渠道记录（增补 1）
3. Agent2 的 Prompt 明确要求交叉验证

任何一环断开，这个场景就失效。这也是为什么它值得单独作为评测集的一个场景（5 条用例）。

## 五、契约层的故障模式

| 故障形态 | 表现 | 本项目中的防线 |
| --- | --- | --- |
| 字段漂移 | Agent2 读不到 labels，或 Agent3 找不到语料编号 | 契约文档 + 各 Prompt 内嵌输出格式 |
| 标识丢失 | 卡片没有 feedback_id，证据链无法下钻 | 增补 2 在调用层强制挂载 |
| 编号虚构 | Agent3 编造的语料编号不在输入里 | 界面解析「语料编号」后与真实 ID 比对，不存在的不生成跳转 |
| 越权输出 | Agent1 顺手给行动建议 | 每个 Prompt 的边界约束段写死 |

## 六、已知取舍

- **逐条调用而非批量。** Agent1 / Agent2 的 Prompt 都是单条设计，一批 N 条反馈需要 2N 次模型调用。原型用 6 路并发池压延迟，但费用压不掉。若追求成本，应把两个 Prompt 改成批量输入，代价是 Prompt 复杂度上升、单条失败会影响整批。
- **历史信号库是静态的。** 原型把 7 天统计写死在 `data.js`。真实系统应由数据层按天滚动计算，并支持按品类、渠道下钻。
- **不做自动执行。** 全部输出停留在建议层。这是刻意的产品选择：客户声音平台的定位是告诉团队该优先做什么，执行闭环交给售后 Agent。
- **标签体系不会自动扩容。** 新信号只被标记，不会自动进入预设标签集。自动扩容需要人工确认环节，否则标签体系会迅速碎片化。
