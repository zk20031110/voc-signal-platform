# VOC 三 Agent 协作：数据契约

> 本文件定义 Agent 之间的接口，以及流水线为串联它们所做的必要设计决策。
> 三个 Agent 的 System Prompt 是唯一事实来源，位于同目录下的 `agent1` / `agent2` / `agent3` 文件。

## 一、相对原始 Prompt 的三处增补

三个 Agent 的 Prompt 以原始版本为基线，只在原文上做加法。全部增补如下，可逐条核对：

| 编号 | 位置 | 增补内容 | 原因 |
| --- | --- | --- | --- |
| 1 | Agent2 · 输入 | 「你会收到该用户在其他渠道的历史反馈记录。若存在跨渠道记录，请交叉验证说法是否一致。」 | 原始 Prompt 一次只接收一张卡，跨渠道矛盾无法被发现 |
| 2 | Agent1 · 输出外层 | 挂载 `feedback_id` 与 `customer_ref` 两个字段 | 卡片需要可追溯；跨渠道关联需要用户标识 |
| 3 | Agent3 · 证据链 | 增加一行「语料编号：F001, F002」 | 让洞察可以下钻回原始语料 |

除上述三处，三个 Prompt 的其余内容未做任何改动。

## 二、端到端数据流

```
反馈批次（含 customer_ref 与渠道）
      |
      v
[ Agent1 信号采集与标注（逐条 / 批量两种输入形态） ]
      in  : single=单条反馈文本；batch=带编号的一批反馈（同一份判定规则）
      out : 标注 JSON + 外层挂载 feedback_id / customer_ref
      |
      v  标注卡片数组
[ 逐条并发调用 Agent2 风险识别与归因 ]
      in  : 单张卡片 + 7 天历史信号库 + 同一用户在其他渠道的反馈
      out : risk_level / risk_reason / attribution / need_human_review / review_reason
      |
      v  风险结果数组
[ 聚合层（非模型组件） ]
      按「风险等级 + 主标签」归组，取组内最严重的等级，
      合并证据编号与原始文本，产出一条聚合风险结果
      |
      v
[ 逐组调用 Agent3 洞察生成与行动建议 ]
      in  : 聚合风险结果 + 7 天历史信号统计
      out : Markdown 洞察报告（含语料编号）
      |
      v
结构化报告 + 可下钻证据链
```

## 三、Agent1 输出契约

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| channel | string | 评价 / 客服 / 退款 |
| sentiment | enum | 正面 / 中性 / 负面 |
| labels | string[] | 从 8 个预设标签中选，可多选 |
| entities.product | string | 商品名称 |
| entities.order_id | string 或 null | 缺失必须填 null，不得编造 |
| summary | string | 一句话概括 |
| is_new_signal | boolean | 无法归入任何预设标签时为 true |
| suggested_label | string 或 null | 仅新信号时给出 |

**预设标签集（8 类）**：质量问题、物流问题、服务问题、尺寸问题、色差问题、包装问题、价格问题、其他。

**两种输入形态**（判定规则只有一份，差别只在输入输出形态）：

| 形态 | 输入 | 输出 | 何时用 |
| --- | --- | --- | --- |
| `single`（默认） | 单条反馈 | 单个标注 JSON | 默认形态，一条失败只影响一条 |
| `batch` | 一批带【反馈 N】编号的反馈 | `{"results":[ ... ]}`，每条结果带 `index` | 要压调用次数时，一次调用处理一批 |

批量形态的输入/输出契约放在 `prompts/agent1-batch-adapter.md`，调用时**追加在 `agent1-collector.md` 之后**，所以标签集、否定句、反讽、新信号两条件等判定规则不存在第二份副本。调用层必须校验 `results` 条数等于输入条数、`index` 恰好覆盖 1..N 且不重复；任一不满足就整块回退逐条重跑，不允许静默丢条目。

**流水线挂载字段**（不属于 Agent1 输出，由调用方附加）：

| 字段 | 含义 |
| --- | --- |
| feedback_id | 原始反馈编号，用于证据下钻 |
| customer_ref | 用户标识，用于跨渠道关联 |

## 四、Agent2 输出契约

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| risk_level | enum | 高 / 观察 / 常规 |
| risk_reason | string | 判断依据，须引用输入中的具体信息 |
| attribution | string | 归因分析 |
| need_human_review | boolean | 涉及安全、健康、品牌声誉必须为 true |
| review_reason | string 或 null | 需复核时说明理由 |

**输入中的历史信号库结构**（本项目实现）：

```
{
  "history_7d": {                    // 过去 7 天各标签的反馈量与情感分布
    "质量问题": { "total": 14, "negative": 11, "trend": "上升" },
    ...
  },
  "recent_24h_negative": 7,          // 24 小时内同类差评数，用于触发阈值规则
  "same_user_other_channels": [ ... ] // 同一用户在其他渠道的反馈原文
}
```

## 五、Agent3 输出契约

Agent3 输出 Markdown，结构固定为两部分：`## 洞察报告` 与 `## 行动建议`。

- 洞察报告含：核心发现、证据链（语料数量 / 来源渠道 / 语料编号 / 原始文本示例）、趋势判断
- 行动建议为表格，列为：优先级、建议内容、预期效果
- 风险等级为高时，开头附加 `⚠️ 需立即关注`

**语料编号行是流水线解析证据链的唯一锚点**：界面通过正则提取 `语料编号：` 后的编号列表，把它们渲染成可点击的标签，点一下跳回左侧原始反馈。

## 六、为什么需要聚合层

Agent2 逐条输出风险判断，Agent3 接收的是「一个」风险识别结果。如果直接对每条反馈调用一次 Agent3，同一批次会产生多份高度重复的报告。

因此在两者之间加入一个纯规则组件（不含模型调用）：

1. 按「风险等级 + 主标签」把风险结果分组
2. 组内取最严重的风险等级作为该组的等级
3. 合并组内所有 `feedback_id` 与原始文本，形成证据链
4. 高风险组内只要有一条 `need_human_review` 为 true，该组即为 true
5. 只为「高」和「观察」两组调用 Agent3；「常规」不生成报告，避免制造噪音

这个组件是刻意的设计取舍：**模型负责判断，规则负责归并。** 把归并交给模型只会增加成本和不确定性。
